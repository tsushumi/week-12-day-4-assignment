# Query Analysis: EXPLAIN ANALYZE before and after indexes

Generated by `npm run analyze` on 2026-11-03. Every number and plan below was produced by running the queries through Prisma's `$queryRawUnsafe` against PostgreSQL; nothing is typed in by hand.

## Test setup

- Database: PostgreSQL 16.15 (Ubuntu 16.15-0ubuntu0.24.04.1)
- Data: 200,000 invoices (table size 19 MB), 500,000 invoice items, 1,000 clients, 5,000 posts
- Invoice status mix: DRAFT=30019, OVERDUE=40196, PAID=89735, SENT=40050
- Method: 1 warm-up run, then 5 timed runs of `EXPLAIN ANALYZE`; the reported time is the **median Execution Time** (the plan shown is the run closest to the median). `VACUUM (ANALYZE)` was run before each phase so statistics are fresh in both.
- "Before" uses the `init` migration only (primary keys and a unique email index, no other indexes); "After" adds the `add_indexes` migration.
- The measurements run in a separate schema (`analysis`) so they never touch the 400-invoice demo data. With only a few hundred rows PostgreSQL correctly prefers a sequential scan even when indexes exist, so a larger dataset is needed for a meaningful comparison.

## Summary

| 1. Filter by Status | 18.39ms | 0.059ms | 312x faster | Parallel Seq Scan -> Index Scan Backward using Invoice_status_createdAt_idx |
| 2. Overdue Invoices (dueDate + status) | 23.17ms | 13.65ms | 1.7x faster | Seq Scan -> Bitmap Heap Scan (Bitmap Index Scan using Invoice_status_idx) |

Absolute times depend on the machine (these ran against a local PostgreSQL with no network latency); the ratios and the plan shapes are what matter. Against a remote database such as Supabase or Neon the "before" numbers are typically larger, because more data has to cross the network and be processed.

## Query 1: Filter by Status

Latest 20 paid invoices (no index on status)

```sql
SELECT * FROM "Invoice"
WHERE status = 'PAID'
ORDER BY "createdAt" DESC
LIMIT 20
```

### Before Index
- Scan type: Parallel Seq Scan
- Rows examined: 200,000
- Execution time: 18.39ms

### After Index
- Scan type: Index Scan Backward using Invoice_status_createdAt_idx
- Rows examined: 20
- Execution time: 0.059ms

### Improvement
- 312x faster
- Rows examined reduced by 99.99% (200,000 -> 20)

### Why

Without an index on `status`, PostgreSQL has to read every invoice, throw away the ones that are not PAID, and sort what is left by `createdAt` (a top-N heapsort) just to hand back 20 rows. The composite index `(status, createdAt)` keeps the PAID invoices already ordered by `createdAt`, so PostgreSQL walks it backwards, stops after 20 entries and never touches the other 199,980 rows. No sort is needed at all. The cost of the query no longer depends on the table size, which is why this is the biggest win of the three.

## Query 2: Overdue Invoices (dueDate + status)

SENT invoices that are past their due date

```sql
SELECT * FROM "Invoice"
WHERE "dueDate" < NOW() AND status = 'SENT'
```

### Before Index
- Scan type: Seq Scan
- Rows examined: 200,000
- Execution time: 23.17ms

### After Index
- Scan type: Bitmap Heap Scan (Bitmap Index Scan using Invoice_status_idx)
- Rows examined: 40,050
- Execution time: 13.65ms

### Improvement
- 1.7x faster
- Rows examined reduced by 80% (200,000 -> 40,050)

### Why

Without an index PostgreSQL scans the whole table and applies both conditions to every row. With indexes it can first narrow the table down to the SENT invoices and only visit those. Note that the planner estimated 28,382 matching rows but only 1,585 really match (see "Planner note for Query 2" below).

## Query 3: Aggregation per Client

Top 10 clients by total paid

```sql
SELECT "clientId", COUNT(*), SUM(total)
FROM "Invoice"
WHERE status = 'PAID'
GROUP BY "clientId"
ORDER BY SUM(total) DESC
LIMIT 10
```

### Before Index
- Scan type: Parallel Seq Scan
- Rows examined: 200,000
- Execution time: 25.92ms

### After Index
- Scan type: Index Only Scan using Invoice_status_clientId_total_idx
- Rows examined: 89,735
- Execution time: 21.35ms

### Improvement
- 1.2x faster
- Rows examined reduced by 55% (200,000 -> 89,735)

### Why

This query has to look at every PAID invoice (about 89,735 of them, roughly 45% of the table) no matter what, because every one of them contributes to a SUM. An index cannot make that disappear. What the covering index `(status, clientId, total)` does is let PostgreSQL answer the query from the index alone (an Index Only Scan, "Heap Fetches: 0") instead of reading the wide table rows, and the entries come back already grouped by `clientId`, so the hash aggregate becomes a cheaper GroupAggregate. That is a real but modest gain: the work is dominated by reading ~90,000 index entries. Measured with the covering index removed (only the five indexes from the assignment): `Bitmap Heap Scan (Bitmap Index Scan using Invoice_status_idx)`, 36.95ms, which is 1.4x slower than the original sequential scan. In other words, the five plain indexes alone make this query slower: the planner is tempted by the `status` index, but fetching ~90,000 rows through it costs more than one sequential pass over the table. Only the covering index, which avoids visiting the table at all, turns it into a gain. For a dashboard that runs this constantly, the next step would be a pre-computed summary table or materialized view.

## Planner note for Query 2

In the "After" run PostgreSQL did **not** use the composite `(status, dueDate)` index that was built for this query. It chose `Invoice_status_idx` and filtered `dueDate` afterwards. The reason is a bad row estimate: the planner expected about 28,382 matching rows, but only 1,585 match. It estimates `status` and `dueDate` separately and multiplies the results, and it does not know that SENT invoices are almost never past their due date (they are usually still inside the 30-day term). With that estimate, the plain `status` index looks cheaper.

To check this, the script drops `Invoice_status_idx` and `Invoice_dueDate_idx` **inside a transaction that is rolled back** (nothing is changed) and runs Query 2 again. With only the composite index available the plan becomes `Bitmap Heap Scan (Bitmap Index Scan using Invoice_status_dueDate_idx)` and the time drops to **1.63ms** (14x faster than the original sequential scan, 8.4x faster than the plan the planner picked with all five assignment indexes).

```text
Bitmap Heap Scan on "Invoice"  (cost=731.34..3698.02 rows=28382 width=61) (actual time=0.472..1.552 rows=1585 loops=1)
  Recheck Cond: ((status = 'SENT'::text) AND ("dueDate" < now()))
  Heap Blocks: exact=1174
  ->  Bitmap Index Scan on "Invoice_status_dueDate_idx"  (cost=0.00..724.24 rows=28382 width=0) (actual time=0.249..0.249 rows=1585 loops=1)
        Index Cond: ((status = 'SENT'::text) AND ("dueDate" < now()))
Planning Time: 0.089 ms
Execution Time: 1.631 ms
```

**Takeaways.** (1) An index on `status` alone is redundant once `(status, createdAt)` and `(status, dueDate)` exist, because PostgreSQL can use the first column of any composite index by itself. It costs write time and disk space and, as shown here, can even lure the planner away from the better index. The assignment asks for all five indexes, so they are all in the schema; in a production system the plain `status` and `dueDate` indexes are the first ones to drop. (2) Always compare estimated rows with actual rows in `EXPLAIN ANALYZE`. A large gap points at statistics, not at a missing index.

## Indexes added by the `add_indexes` migration

| Index | Columns | Used by |
|---|---|---|
| `Invoice_clientId_status_idx` | clientId, status | per-client invoice lists filtered by status |
| `Invoice_dueDate_idx` | dueDate | (not chosen by the planner for these queries) |
| `Invoice_status_clientId_total_idx` | status, clientId, total | Query 3 (covering, Index Only Scan) |
| `Invoice_status_createdAt_idx` | status, createdAt | Query 1 |
| `Invoice_status_dueDate_idx` | status, dueDate | Query 2 (best plan when it is the only candidate) |
| `Invoice_status_idx` | status | Query 2 (after) |

Two more indexes support the N+1 fix and relation loading: `InvoiceItem_invoiceId_idx` and `Post_authorId_idx`. PostgreSQL does not index foreign-key columns automatically, so without them "all posts of these authors" is a scan of the whole `Post` table.
